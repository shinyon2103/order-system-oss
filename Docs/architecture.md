# 注文システム アーキテクチャ設計

## 1. 目的と対象範囲

文化祭などの模擬店で、販売済みチケットを確認しながら注文を受付し、受付・調理・受け渡し・表示を同じ注文状態に同期する。

本システムは販売・決済・チケット販売管理を担当しない。チケット番号は受付時の照合キーとして扱う。

## 2. 初期方針

| 項目 | 方針 |
| --- | --- |
| 実行基盤 | Cloudflare Workers |
| 永続データ | Cloudflare D1 |
| 競合制御 | Durable Objects の単一キューインスタンス |
| リアルタイム更新 | Durable Object が受け付ける WebSocket |
| クライアント | タッチ操作を前提にしたPWA |
| オフライン | 初期版は再接続・状態表示を優先。注文確定の完全オフライン化は後段 |
| 運用単位 | このクラスの模擬店のみ。複数組織向けの管理は対象外 |
| 外部出力 | まずCSV、Google Sheets連携は後段 |

CloudflareのWorkerをAPIと静的アセットの入口にし、D1を業務データの正本とする。Durable Objectは、複数の調理端末が同時に次の注文を要求する際の直列化と、接続中画面への通知を担当する。

## 3. コンポーネント

```text
ブラウザ/PWA
  ├─ 受付画面
  ├─ 調理画面（複数端末）
  ├─ 受け渡し画面
  ├─ お客さん向け表示
  ├─ お客様自身の注文状況照会
  └─ 管理画面
       │ HTTPS / WebSocket
       ▼
Cloudflare Worker
  ├─ 認証・端末権限チェック
  ├─ 入力検証・APIルーティング
  ├─ D1読み書き
  └─ OrderQueue Durable Objectへの転送
       ├─ 注文割り当ての直列化
       └─ 接続画面への状態通知
       │
       ▼
Cloudflare D1
  ├─ 営業日・設定
  ├─ 注文
  ├─ 注文明細
  ├─ メニュー・選択肢
  ├─ 端末・管理者・セッション
  └─ 操作履歴
```

## 4. Durable Objectの責務

初期版では、営業日単位の `OrderQueue` インスタンスを1つ作る。全調理端末の `next` 要求をこのインスタンスに集約し、次の処理を1回の直列化された操作として扱う。

割り当て処理は次の条件を満たす必要がある。

1. 最古の `WAITING` 注文を選ぶ。
2. 同じ営業日で生存確認が有効な、稼働中・非離席・担当なしの調理端末を抽出する。
3. 最終調理完了時刻が最も古い候補（完了実績なしを先行）である要求元だけに割り当てる。
4. `COOKING` と開始時刻を記録する。
5. 割り当て結果を要求元へ返す。
6. 状態変更を購読中の画面へ通知する。

単純な `SELECT` と別の `UPDATE` をWorker側で実行する方式は採用しない。Queue DO内で要求を直列化し、同じ注文を複数端末に返さないことを最重要の不変条件とする。

## 5. 状態の正本と通知

- D1は注文・端末・履歴の永続的な正本とする。
- Durable Objectのメモリ上のMapやWebSocket接続一覧は、正本ではなく一時的な接続管理情報とする。
- WebSocketが切断・再接続した場合、画面はAPIから現在状態を再取得してから購読を再開する。
- 通知を受信できなかったことを前提に、画面は通知だけで状態を確定しない。

WebSocketはDurable ObjectのHibernation WebSocket APIで実装する。ブラウザ側は切断時に指数バックオフで再接続し、再接続後はAPIから現在状態を取り直す。

## 6. メニュー管理

メニューはコードに固定せず、管理画面から編集できるデータとして扱う。商品に対して、味付け・サイズ・追加トッピングなどのサブ項目を複数登録できる。

- 商品：焼きそば、たこ焼きなどの販売単位
- サブ項目グループ：味付け、サイズ、トッピングなど
- 選択肢：ソース味、塩味、大盛りなど
- 注文時：商品名・サブ項目名・選択肢名を明細へスナップショット保存

調理画面は注文時点のスナップショットを表示し、後からメニューを変更しても受付済み注文の内容が変わらないようにする。

## 7. 認証とセッション

管理者端末で管理者のログイン名とパスワードを初期設定する。ログイン後に端末セッションを発行し、管理画面から通常のセッション期間と通信断復旧時の再認証猶予を変更できるようにする。

- 初回起動時はセットアップ画面で管理者アカウントを作成する。
- パスワードは平文保存しない。
- パスワード忘れ時は、DBまたは環境変数を使った管理者による手動リセットを行う。
- 30分以内に通信が復旧した場合は、受付端末の未送信注文を再認証なしで送信できるようにする。
- 30分の再認証猶予は管理画面で変更可能な設定値とする。
- 再認証不要の判定は端末の時計だけに依存せず、最後の認証状態とサーバー時刻を基準にする。

営業日の作成・開始・終了は管理画面で行う。受付・調理・受け渡し・表示画面は、管理画面で `OPEN` にされた営業日を自動的に利用し、端末ごとの営業日ID入力を要求しない。

発番位置は営業日ごとにD1へ保持する。終了した同じ営業日を再開すると保存位置を復元し、保存位置が設定上限を超えている場合のみ設定下限へ戻す。営業中に上限へ達したときの受付停止は維持する。

## 8. セキュリティ境界

- 端末登録情報に基づく役割をAPI側で検証する。
- UIでボタンを隠すだけの権限管理は行わない。
- 管理API、端末認証付き一覧表示API、認証不要の最小注文状況APIを分離する。
- チケット番号だけを秘密情報や認証情報として扱わない。
- 注文作成、状態遷移、CSV出力を監査可能な操作として記録する。
- 管理者は注文ごとの状態遷移、操作端末、操作ID、取消理由を管理画面から確認できる。
- ログイン名とパスワードによる認証を行う。
- 運用端末は管理画面で発行した端末IDと端末キーで認証し、Workerが `RECEPTION` / `KITCHEN` / `DELIVERY` の役割をAPIごとに検証する。
- 端末キーは十分な乱数から生成し、D1にはSHA-256ハッシュだけを保存する。固定長ハッシュはWorkers Web Cryptoの定時間比較で照合し、キー再発行時は旧キーを即時失効させる。管理者パスワードと初回セットアップトークンも同じ定時間比較を使用する。
- 一覧表示は`DISPLAY`端末キーで保護する。認証不要の注文状況APIは入力番号自身の状態と前方件数・商品点数だけを返し、WebSocket通知にも商品内容を含めない。

## 9. 障害時の基本方針

- WebSocket切断時は指数バックオフで再接続する。
- 画面上にオンライン・再接続中・オフラインを表示する。
- 調理画面は再接続後に、自端末へ割り当てられた注文を再取得する。
- 同じ完了操作を再送しても二重遷移しないよう、注文状態と操作IDを検証する。
- 受付端末は通信断中も注文を確定し、ブラウザの一時保存領域に未送信キューとして保存する。
- `navigator.onLine` がオンラインでもWorkerへ到達できない場合は通信断として扱い、再認証猶予内なら同じ冪等性キーの注文を未送信キューへ退避する。
- 未送信注文には受付時刻、注文ID、冪等性キーを保持する。
- 復旧後に受付時刻の古い順でサーバーへ送信する。
- 受付画面に未送信件数と同期失敗を表示し、失敗時は手動で再送できるようにする。
- 受け渡し画面と公開表示は、一時的な取得失敗時に直前の一覧を消さず、古い可能性があることを明示する。
- 調理完了・提供済み操作は送信中の二重操作を防ぎ、失敗時は同じ画面で再試行できるようにする。調理完了のSpace／Enter操作は長押しと短時間連打を抑止する。
- 割り当て、調理完了、提供完了、管理者復旧、取消、受け渡しからの再調理は営業日単位のQueue DOで直列化する。再調理時に前担当端末が別注文を持つ場合は、その注文を待機へ戻す処理と対象注文の復帰を同じD1 batchで記録する。
- サーバーの登録時刻と受付時刻を分け、キュー順序は受付時刻を基準にする。
- 同じ注文の再送は冪等性キーで重複登録を防ぐ。

## 10. 実装フェーズ

1. この資料と注文フロー・DB・API仕様の確認
2. Workersプロジェクトとテスト基盤の初期化
3. D1マイグレーションとモデル層
4. 受付・調理・受け渡しのAPI
5. Durable Objectによる調理キュー
6. WebSocket通知
7. 最小画面
8. 表示・管理・CSV
9. 再接続、オフライン表示、負荷・競合テスト

2026-08-21時点で1〜9の基盤は実装済み。PWAのアプリシェルはService Workerでキャッシュし、受付の未送信注文はIndexedDBへ保存する。ブラウザがオンライン判定のままWorkerへ到達できない場合も未送信キューへ退避し、件数と同期状態を受付画面へ表示する。調理端末は再読み込み・再接続時に同じ端末へ割り当て済みの`COOKING`注文を復元する。ChromebookのスリープやBFCacheから画面へ戻った場合は、端末認証、未送信同期、現在状態、WebSocket接続を再確認する。調理通知音は端末上の明示操作でWeb Audioを準備し、新しい注文IDへ切り替わった時だけ鳴らす。受け渡し・公開表示は通信断中も直前の一覧を保持する。管理画面の当日状況はWebSocket通知で追従し、保険の定期更新はWebSocket切断中だけ実行する。注文数が変わらない調理開始・調理完了・提供完了・待機戻しでは商品別集計を省略し、通信失敗時も直前の一覧を保持する。`WAITING`注文の管理者取消は営業日単位のQueue DOで割り当てと直列化し、注文単位の監査履歴を管理画面から確認できる。競合テストでは100件を5台で処理し、重複と欠番がないことを検証する。

## 11. 未決事項

- 調理端末が注文を保持したまま切断された場合の再割り当て条件。
- Cloudflareアカウント、Workersの本番名、利用ドメイン。
- ブラウザの一時保存領域が消去された場合の復旧手順。
- 受付端末の未送信注文を別の端末へ引き継ぐか。
