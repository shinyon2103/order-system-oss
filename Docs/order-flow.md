# 注文フロー・状態遷移

## 1. 注文状態

| 状態 | 意味 | 次の状態 |
| --- | --- | --- |
| `WAITING` | 受付済み、調理待ち | `COOKING`, `CANCELLED` |
| `COOKING` | 調理端末に割り当て済み | `READY`, `WAITING`（再割り当て時） |
| `READY` | 調理済み、受け渡し待ち | `COOKING`（再調理）, `COMPLETED` |
| `COMPLETED` | 提供済み | なし |
| `CANCELLED` | 取消済み | なし |

初期実装では通常運用の主経路を `WAITING → COOKING → READY → COMPLETED` とする。取消と再割り当ては管理権限または障害対応用の操作として、通常画面から分離する。

## 2. 受付

1. 受付担当が端末役割 `RECEPTION` で画面を開く。
2. チケット番号を入力する。
3. 商品と数量を入力・確認する。
4. Workerが入力値と端末権限を検証する。
5. 端末側で受付時刻と冪等性キーを確定する。
6. 通信可能ならサーバーへ送信し、初期状態を `WAITING` としてD1に保存する。
7. 通信断中、またはブラウザがオンライン判定でもWorkerへ到達できない場合は、ブラウザの一時保存領域に同じ冪等性キーのまま未送信キューとして保存し、受付画面では受付完了として扱う。
8. 復旧後、受付時刻の古い順に未送信注文をサーバーへ送信する。
9. サーバーは冪等性キーで再送による重複登録を防止する。
10. 登録後、Queue DOへ新規注文イベントを通知する。
11. 調理画面と管理画面へ更新を通知する。

注文作成の再送に備え、受付端末が生成した `request_id` を冪等性キーとして扱う。端末内の受付時刻と、サーバーへ登録した時刻は別項目として保持する。

## 2.1 オフライン受付と再認証

受付端末は最後に認証済みとなった状態と、サーバーが発行した再認証猶予期限を端末内に保持し、期限内の通信断中だけ受付操作を許可する。未送信注文はブラウザの一時保存領域に保持し、受付画面へ件数と同期状態を常時表示する。オンライン復旧時は、未送信注文を送る前に端末キーをサーバーで再検証して猶予期限を更新する。送信失敗時はキューを残し、画面から再送できる。初期値は30分とし、期限を超えたオフライン状態では受付画面をロックする。

## 3. 調理端末への割り当て

1. 調理端末が `device_id` を付けて次の注文を要求する。
2. WorkerはQueue DOへ要求を転送する。
3. Queue DOは要求を直列化する。
4. Queue DOは最古の `WAITING` 注文を1件だけ選択する。
5. 注文を要求元へ割り当て、`COOKING` と開始時刻を記録する。
6. 注文番号と明細を調理端末へ返す。
7. 他の画面へ状態変更を通知する。
8. 調理端末で通知音を準備済みの場合、新しい注文IDへ切り替わった時だけ短い通知音を鳴らす。
9. 離席中の調理端末には新しい注文を割り当てない。

同時要求が発生しても、各要求はQueue DO内で順番に処理される。重複防止はテストで明示的に検証する。

ブラウザの自動再生制限に対応するため、通知音は調理担当が画面上のボタンを押して準備する。設定は端末に記憶するが、ページ再読み込み後は再度ボタンを押して音声を準備する。同じ割当の再取得やWebSocketの重複通知では鳴らさない。

## 4. 調理完了

1. 調理担当が表示内容を確認する。
2. 大きな「調理完了」ボタン、またはSpace／Enterキーを1回実行する。長押しのキーリピートと短時間の連打は無視する。
3. APIは注文が当該端末に割り当てられた `COOKING` 状態か確認する。
4. `READY` とサーバー時刻を保存する。
5. 受け渡し画面・READY表示へ通知する。
6. 調理端末は次の注文を要求する。

通常稼働中は完了後すぐに次の注文を要求する。「この注文の完了後に離席」を選択済みの場合は次の注文を受け取らず離席表示へ移る。別端末や古い画面からの完了操作は拒否する。二重送信は同じ結果を返すか、既に完了済みであることを明示して安全に終了する。

### 4.1 離席

- 担当注文がない場合は、そのまま離席状態へ変更する。
- 担当注文がまだ調理開始前の場合は、画面で受付番号と未着手であることを確認した後、`WAITING`へ戻して離席する。
- すでに調理を開始している場合は、担当を維持したまま「この注文後に離席」とし、完了後に新しい注文を割り当てない。
- 離席解除後は通常の自動割り当てへ戻る。

## 5. 受け渡し

1. `DELIVERY` 端末は `READY` の注文だけを表示する。
2. 担当者はチケット番号と内容を照合する。
3. 提供済み操作を実行する。
4. APIは `READY` 状態を確認する。
5. `COMPLETED` と提供時刻を保存する。
6. READY表示から注文を除外する。

受け渡し前に再調理が必要な場合は「調理中に戻す」を実行する。対象は前回の担当調理端末へ戻す。その端末がすでに別注文を担当している場合は、別注文を `WAITING` へ戻してから、再調理対象を `COOKING` として優先表示する。

## 6. 表示・お客様照会

- 調理中表示は `COOKING` のチケット番号を表示する。
- 調理済み表示は `READY` のチケット番号を表示する。
- 一覧表示画面は`DISPLAY`端末キーを必要とし、書き込み権限を持たない。
- 認証不要の注文状況ページでは、入力された受付番号自身の状態と、調理待ち中に前にある注文数・商品点数だけを表示する。
- 認証不要ページには明細、備考、担当端末、内部注文IDを含めない。

## 7. 例外フロー

### 調理端末の切断

切断だけでは即時に `WAITING` へ戻さない。誤った再割り当てを防ぐため、管理画面で対象注文を確認して「調理待ちへ戻す」を実行する。この操作では元の調理端末を同時に離席状態へし、同じ端末への即時再割り当てを防ぐ。別端末はQueueから取得できる。自動タイムアウトの導入は実運用テスト後に判断する。

### 完了操作の通信断

通信断中に調理完了を実行した場合は、注文ID、端末ID、受付番号、完了時刻と操作IDを端末内へ保存し、画面では調理完了として扱う。オンライン復帰後、同じ操作IDで完了APIへ自動送信し、サーバーが受理した後にだけ端末内の同期待ち状態を削除する。再送時も同じ操作IDを使い、同じ操作を複数回適用しない。

サーバーへ完了状態が同期されるまで次の注文は割り当てられない。画面には、追加の注文を確認するにはオンライン復帰を待つか、受付・管理担当へ直接聞く必要があることを明示する。同期に失敗した場合は完了状態を端末内に残し、オンライン時に手動再試行もできるようにする。

### 注文の取消

管理画面では注文一覧から直接、受付画面では受付番号を入力して注文詳細を表示した後に、確認付きで取り消す。通常は`WAITING`、`READY`、`COMPLETED`を対象とし、取消理由、操作ID、管理者IDまたは受付端末IDを状態履歴へ残す。管理者に限り`COOKING`も強制取消できるが、理由入力後に受付番号を再入力する二段階確認を必須とする。受付端末からは`COOKING`を取り消せない。

## 8. 不変条件

- `WAITING` の注文は、同時に2台以上へ割り当てられない。
- `COOKING` の完了操作は、割り当てられた端末以外から実行できない。
- `READY` 以外の注文を提供済みにできない。
- 業務時刻はサーバー側で記録する。
- 状態変更は監査履歴に残す。

## 8.1 直前操作の取り消し

- 受付・調理・受け渡し端末、および管理画面の注文操作は、成功後10秒間だけ元に戻せる。
- 期限はWorkerのサーバー時刻で判定し、操作した端末または管理者本人だけが実行できる。
- 後続の状態変更がある場合は安全のため拒否する。ただし、調理完了直後に同じ端末へ自動割当された次注文は待機へ戻し、元の注文を同じ端末へ復元する。
- 取り消し操作自体も `order_status_history` に記録し、注文を物理削除しない。

## 9. 未決事項

- チケット番号の形式と、受付番号を再利用する運用の可否。
- 調理端末が注文を保持したまま切断された場合のタイムアウトと再割り当て条件。
- 受付番号は営業日の開始・切替時と、開始中の営業日名・日付を変更した時に設定済みの開始番号へ戻す。同じ営業日内で番号を手動リセットする場合は、紙伝票との重複に注意する。
- ブラウザの一時保存領域が消去された場合の復旧手順。
- 1チケットに対して複数注文を許可するか。
- 調理端末切断時のタイムアウトと再割り当て条件。
- 取消・返金相当の運用を必要とするか。
- 公開表示で明細を表示するか、番号だけにするか。
